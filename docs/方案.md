# 文档解析 + 清洗入库服务 — 方案

## 1. 背景与目标

构建一条 "文档 → 结构化文本" 的解析流水线:

- 上游:本地部署在 **Docker 容器** 里的 MinerU(官方 `mineru-api`,默认端口 8000)。
- 下游:RAG / GraphRAG 入库(本版只做到"解析 + 清洗落盘",不直接推库)。
- 入口:一个 **FastAPI 服务**,统一接收文件上传,转发给 MinerU,清洗后落盘。

本次要解决的核心问题:MinerU 只负责"把 PDF/文档变成结构化文本",不做语义层面的数据质量工作。直接入库会带入页眉页脚、页码、重复段、碎片段等噪声——尤其对 GraphRAG 的实体/关系抽取影响很大。因此 MinerU 之后必须再加一轮清洗。

## 2. 架构与数据流

```
客户端 ──HTTP──▶ FastAPI 服务(本机, uvicorn)
                    ├─ 路由层   routers/parse.py
                    ├─ 配置层   config.py  (pydantic-settings 读 .env)
                    ├─ MinerU 客户端 mineru_client.py (httpx 转发)
                    ├─ 清洗层   cleaning.py
                    └─ 存储层   storage.py  (落盘 md/json)
                          │ httpx multipart
                          ▼
              MinerU Docker 容器(http://127.0.0.1:8000, /file_parse)
```

数据流:

```
上传文件 → 校验格式 → 转 Multipart 调 MinerU /file_parse
       → 取 md_content + 结构化 json → 清洗
       → 落盘 {output_dir}/{doc_id}/ → 返回结果 + 落盘路径
```

## 3. 接口设计

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | `/parse` | 同步解析。multipart 上传 1..N 个文件,逐个转调 MinerU `/file_parse`,清洗后落盘,返回结果 |
| GET  | `/health` | 本服务健康 + 探测 MinerU `/health`(透传其元数据) |

`POST /parse` 请求:`files: List[UploadFile]`(可多文件)。

`POST /parse` 响应(每个文件一个 `FileResult`):

```json
{
  "results": [
    {
      "filename": "sample.pdf",
      "doc_id": "a1b2c3_1690000000",
      "success": true,
      "page_count": 12,
      "clean_md": "# 标题\n正文...",
      "files": {
        "raw_md": "output/a1b2c3_1690000000/raw.md",
        "raw_json": "output/a1b2c3_1690000000/raw.json",
        "clean_md": "output/a1b2c3_1690000000/clean.md",
        "clean_json": "output/a1b2c3_1690000000/clean.json",
        "meta": "output/a1b2c3_1690000000/meta.json"
      },
      "stats": { "removed_page_numbers": 12, "removed_headers": 4, "removed_duplicates": 3 },
      "error": null
    }
  ]
}
```

- 响应默认带清洗后 markdown 正文;加 `return_content=false` 可只返回落盘路径(大文件)。
- MinerU 本身是异步任务模型(上传→建任务→轮询→下载),本服务已封装该链路并对 `/parse` 阻塞等待完成,对外表现为同步接口。

## 4. 配置项(.env)

```ini
# MinerU(跑在 Docker 容器,映射端口;v1 协议)
MINERU_API_BASE_URL=http://127.0.0.1:8008
MINERU_API_PREFIX=/v1
MINERU_TIMEOUT=600             # 单次 HTTP 请求超时(秒)
MINERU_POLL_INTERVAL=2         # 轮询任务状态间隔(秒)
MINERU_MAX_WAIT_SECONDS=1800   # 等待任务完成的最大时长(秒)
MINERU_OUTPUT_FORMATS=markdown,middle_json   # 逗号分隔
MINERU_TIER=                   # 可选 flash/basic/standard/advanced,留空用默认
MINERU_OCR_MODE=auto           # auto/txt/ocr

# 本服务
UPLOAD_DIR=./uploads
OUTPUT_DIR=./output
MAX_UPLOAD_MB=50
```

`config.py` 用 `pydantic-settings.BaseSettings` 读取,字段与上面一一对应,缺失时用默认值。MinerU 的地址、前缀、输出格式、轮询参数全部在此调整,无需改代码。

## 5. MinerU 部署与调用说明

### 5.1 Docker 部署

本机 MinerU 以 Docker 容器形式运行,API 服务映射到宿主机端口 **8008**(MinerU v4.0.5)。`MINERU_API_BASE_URL` 指向 `http://127.0.0.1:8008`(按实际映射端口调整)。

### 5.2 v1 协议(OpenAI Files 风格)

MinerU v4 的 API 是异步的,分「上传 → 解析 → 下载」三步:

| 端点 | 方法 | 说明 |
|------|------|------|
| `/v1/health` | GET | 服务健康、版本与支持的输出格式 |
| `/v1/uploads` | POST | 创建上传,返回 `upload_id` |
| `/v1/uploads/{id}/content` | PUT | 上传文件原始字节 |
| `/v1/uploads/{id}/complete` | POST | 完成上传,返回 `file_id` |
| `/v1/parse/jobs` | POST | 提交解析任务(引用 `file_id`),返回 `job_id` |
| `/v1/parse/jobs/{job_id}` | GET | 轮询任务状态 |
| `/v1/files/{file_id}/content` | GET | 下载解析结果(markdown / middle_json 等) |

调用流程:

```
POST /v1/uploads                  -> upload_id
PUT  /v1/uploads/{id}/content     (原始字节)
POST /v1/uploads/{id}/complete    (sha256sum) -> file_id
POST /v1/parse/jobs   {files:[{source:{type:"file_id",file_id}}]} -> job_id
轮询 GET /v1/parse/jobs/{job_id}  直到 status ∈ completed/failed
GET  /v1/files/{file_id}/content  下载 markdown / middle_json
```

本服务已在 `mineru_client.py` 封装整条链路,并做轮询等待与超时控制。

### 5.3 关键注意

- 支持的输出格式(以 `/v1/health` 返回的 `features.output_formats` 为准):`markdown / middle_json / structured_content / zip`。
- 支持的文件来源:`file_id / url / inline`;本服务统一走 `file_id`(先上传)。
- 任务状态:`queued / running / completed / partial / failed / canceled`。

## 6. 清洗规则(本服务核心)

按 `clean(md_text) -> clean_md` 顺序执行,规则参数可调:

1. **页码** — 删除独立成段的纯数字、`第 N 页`、`Page N`、`- N -` 等。
2. **页眉/页脚** — 按 `(文本 hash, 归一化位置)` 统计跨页重复出现的文本块,出现页数超阈值(默认 ≥3 页)判为页眉/页脚并删除。
3. **空段/短段** — 去空白行、去除长度 < 2 字符的无意义段。
4. **去重** — 块级 hash 去重(连续重复行合并 + 全局重复块去重)。
5. **结构规整** — 保留 MinerU 已标注的标题层级;对"上一行非标点结尾"的碎段做轻量合并(可开关)。
6. **统计** — 记录清洗前后块数、字符数、删除的页码/页眉/重复块数量,写入 `meta.json`。

## 7. 目录 / 存储约定

落盘到 `{OUTPUT_DIR}/{doc_id}/`:

| 文件 | 说明 |
|------|------|
| `raw.md` / `raw.json` | MinerU 原始输出(留档) |
| `clean.md` / `clean.json` | 清洗后结果 |
| `meta.json` | 来源文件名、解析时间、页数、清洗统计 |

`doc_id` 用 `文件名 hash + 时间戳` 生成,避免同名覆盖。

## 9. 验证步骤(端到端)

1. 准备样例 PDF,确认 MinerU 容器已启动:`curl http://127.0.0.1:8008/v1/health`。
2. `cp .env.example .env`,按实际端口改 `MINERU_API_BASE_URL`。
3. 启动服务:`uvicorn app.main:app --reload --host 0.0.0.0 --port 8001`。
4. 调接口:

   ```bash
   curl -F "files=@sample.pdf" http://192.168.31.15:8001/parse
   ```

5. 校验:返回 `success=true`;`{OUTPUT_DIR}/{doc_id}/` 下出现 `raw.md`、`clean.md`、`meta.json`;`clean.md` 已无页码/页眉,段落规整。
6. 再上传 txt/csv/docx 各一份,确认服务不崩溃、错误可读(记录 MinerU 对非 PDF 的实际行为,作为后续回退依据)。
